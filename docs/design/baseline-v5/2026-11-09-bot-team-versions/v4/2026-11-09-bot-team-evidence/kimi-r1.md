VERDICT: REVISE

## P0（阻止按文档安全实现或满足原需求）

### P0-1 缺少“不静默换模型/运行时”的显式绑定规则
- **章节**：§11.1、§11.2、§16
- **具体冲突**：文档只规定“不在工作途中静默换主机或换执行器”（§11.1）和“不能静默换供应商”（§16），但未把**模型/运行时标识作为 binding 的不可变属性**。当默认模型/运行时不可用时，实现者仍可在同一供应商内切换到其它模型，或在“能力等价”借口下切换运行时，从而违背聚焦#2的“不静默换模型”。
- **最小修订**：在 §11.2 能力合同中增加 `modelId`/`runtimeCanonicalId` 为 binding 核心字段；任何变更必须生成新 `bindingRevision` 并经用户确认。UI 在执行卡片/工作详情中展示实际使用的 model/runtime，fallback 必须显式授权。

### P0-2 canonical runtime ID 兼容缺口仍无映射规则
- **章节**：§3.2、§11.4
- **具体冲突**：文档已承认“项目 CLI registry 与 Room discussion_only 不等价且 xiaok-cli ID 有兼容缺口”，但只写“P0 先归一 canonical runtime ID 并验合同”，未给出映射表、维护方、探测失败时如何提示。没有这些规则，P0a 的“项目与 Room 路径均真实跑通”无法被客观验收。
- **最小修订**：在 §11.4 增加 canonical ID registry 示例（含 registry ID、Room 识别符、项目 harness ID、能力维度），并规定探测失败的“具体缺项”提示文案；P0a 验收必须包含 mapping 自动化测试和 registry 变更审计。

### P0-3 小K助理共用主动机制缺少集成契约
- **章节**：§9、§13
- **冲突**：文档提出“将共用主动机制接到小K助理”，但未定义主动消息如何进入现有小K助理对话流、未读状态由谁写入、助理模型回复上下文如何引用这些消息、旧顶部建议是否关闭。聚焦#3 要求的“消息感知、未读、回复上下文”因此无法保证。
- **最小修订**：在 §9 增加“小K助理 adapter 契约”：消息体字段（`messageId`、`sourceType`、`goalId`、`artifactRef`、`readCursor`、`revoked`）、写入/更新接口、上下文包组成规则；P0c 验收必须覆盖 App 前台关闭/重新打开后助理对话的未读一致性。

### P0-4 外发/高影响操作未形成清单与默认确认规则
- **章节**：§15
- **冲突**：§15 泛称“对外发送、合并、删除、付费等动作依用户的具体授权策略处理”，但未列举哪些 Bot/Agent 行为属于“外发/高影响”，也未规定默认必须确认的最小集合。聚焦#4 的“外发”要求因此落空。
- **最小修订**：在 §15 增加外发/高影响动作清单（至少包括：跨网络发送数据、IM/邮件/API 外发、代码合并/发布、删除/覆盖文件、付费/配额消耗、本地 shell 执行/写盘），并规定默认必须用户确认，除非存在匹配内容摘要的常设授权。

### P0-5 缺少全局撤销与紧急停止入口
- **章节**：§7、§8、§15
- **冲突**：文档有“暂停主动性”（不取消已启动工作）、“停止按钮”（针对单个 run）、“改派”（针对单个任务）、单条授权撤销，但没有用户可一键撤销某个 Bot/群/来源的权限并立即取消相关运行/排队的机制。聚焦#4 的“撤销”不完整。
- **最小修订**：在 §15 增加“全局撤销/紧急停止”：用户可撤销 Bot、群或来源的授权；撤销后未开始工作被取消、运行中 run 被发送取消、后续消息/摘要不再携带已撤销正文；UI 在群详情和运行卡片提供该入口。

## P1（重要，需在实施前收敛）

### P1-1 验收矩阵 A01-A26 未映射到里程碑
- **章节**：§17、§18
- **冲突**：所有 A01-A26 都作为“真实场景验收矩阵”，但未说明哪些是 P0a/P0b/P0c、哪些可后移到 P1，容易导致首发范围膨胀、测试不可执行。
- **最小修订**：在 §18 增加“所属里程碑”列，例如 A01-A05/A06/A07/A08/A09/A10/A11/A12/A25 为 P0b，A16-A18/A20-A22 为 P0c，其余可标记为 P1。

### P1-2 主动触发的“重要性/行动价值门槛”无量化
- **章节**：§8、§9
- **冲突**：事件触发依赖“重要性与行动价值达到门槛”，但没有默认阈值或可配参数，无法验证聚焦#3 的“主动性”不会变成骚扰。
- **最小修订**：在 §9 增加默认门槛示例，例如“仅当影响已承诺下一步、需要用户决策、或用户显式启用 research 时才投递；非晨间主动消息每日上限默认值”，P0c 用 A17/A18 验证。

### P1-3 恢复/重连后继续执行的条件不足
- **章节**：§11.3、§14
- **冲突**：§11.3 禁止自动重放，但未明确“恢复”是系统自动还是必须用户点击，以及 host/binding/project 一致后是否可无副作用自动继续。
- **最小修订**：在 §14 Run 状态机增加 `resuming → running` 转换条件：仅当 host/binding/project/runId 一致且无未确认外部副作用，或用户显式确认后才可继续；否则进入 `unknown`/`waiting_input`。

### P1-4 后台服务安装/升级/版本握手验收缺失
- **章节**：§13、§17
- **冲突**：文档要求“用户级后台服务管理共享核心生命周期”，但里程碑中未列出服务安装、自升级、协议不兼容时的降级验收。
- **最小修订**：在 §17 P0a 硬门槛增加“后台服务可在目标平台完成安装/自升级/与两客户端握手；协议不兼容时进入只读/等待升级，不半成功派工”。

### P1-5 Handoff 无超时与拒绝后的升级路径
- **章节**：§7、§14
- **冲突**：交接结构完整，但 handoff 状态机没有 `offered` 超时、拒绝/无响应后的自动升级规则，可能导致工作挂起，影响聚焦#1 的“闭环”。
- **最小修订**：在 §14 Handoff 状态机增加 `offered` 超时→用户升级、`rejected`→原 owner 继续或用户改派，并给出默认超时（如 5 分钟）。

## 非阻断建议

- **§6 “零专用配置”与实际引导**：已在正文中说明“缺凭据时明确引导”，建议在 §6 标题或步骤 1 中再强调“首次连接仍需完成运行环境/凭据引导”，避免市场口径与产品体验错位。
- **§5 提供运行时/能力矩阵示例**：帮助设计、前端与后端对齐“仅讨论/可读/可改/可执行/可停止”的展示状态。
- **§20 评审冲突裁决**：说明当真实 CLI 评审者对同一问题结论冲突时，由作者提供复现/证据并复评，避免“已发起评审”掩盖未决项。
