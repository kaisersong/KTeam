## P0（阻止安全实现或阻止满足原需求）

### P0-1 §6.4 / §7 / §8 / §17 / §18-A11：相关性路由是核心能力，却没有可判定门槛，也没有探针
- **冲突**：§1 首要验收与 §2 全部场景都依赖“未@的自然语言由目标/承诺/能力/上下文决定相关成员”。但：①§17 P0a 的探针清单只有“复用链、canonical ID、原生+一种外部完整执行探针、单owner服务边界、原型”，不含路由与触发管线；②A11 通过条件是“相关成员响应；无必要时安静，不默认全员模型调用”，无语料、无指标、无阈值，不可判定；③用户给定的事实是 OpenDuet 群聊为“未@时按成员顺序依次响应”，即现状回退路径恰好是 §7/§8 明令禁止的行为，而文档只写“补事件选择与相关成员路由”，没有说明探针失败时 P0b 是否允许带病进入。
- **最小修订**：在 §17 P0a 增加“路由探针”交付项；在 §18 固定一份标注语料（目标+能力矩阵+若干条群消息，标注期望响应成员与期望 noop），A11 改为可判定条件，例如：期望响应集合命中率 ≥ 阈值、非期望成员被唤醒数 ≤ N、noop 用例 100% 安静、单条消息模型调用次数 ≤ 1 次路由判断；同时写明探针未达标时 P0b 只能交付“用户显式 @/指名”版本，不得以顺序全员应答代替。

### P0-2 §14 / §16 / §9 / §8 / §18-A17、A22：Run/Wake 状态机无法表达文档承诺的状态
- **冲突**：§14 Run 只有 `queued→admitted→running→waiting_input/approval→completed/failed/cancelled`（+stopping/unknown）。但文档同时承诺：§8“预算耗尽后保存检查点，说明已做/剩余/成本，由用户续行”、§9“暂停主动性阻止新调度但不取消已启动工作”、§16 用户状态含“主机离线/额度不足/已暂停”、§13“过期任务按规则跳过或询问”。这些都没有对应 Run/Wake 状态或转换，§14 最小实体里也没有 checkpoint。后果是：被预算或离线挂起的工作只能显示为 running 或 failed，直接违反 §1/§16“不把未完成显示成完成/工作中不刷成未读”的可信度要求。
- **最小修订**：Run 增加 `waiting_budget / waiting_host / paused / expired` 及其恢复与终态规则；§14 实体增加 checkpoint（含已做/剩余/成本快照）；给“过期”定义具体判定（如 wake_job 的 `validUntil` 或 due 后超过 T 且来源版本未变即过期），并把 A17 的“不无条件补跑过期动作”改为引用该阈值。

## P1（按文档实现会出现明确错误行为，应在对应阶段前修）

### P1-1 §7 / §14：单 owner 缺少数据级唯一约束与仲裁
- **冲突**：§7 要求“每项工作只能有一个当前负责的执行owner”“accept 原子认领”，§14 唯一键只覆盖 `(conversation,event,bot,decisionRevision)`、`(commitment,revision,due)`、`(originRun,deliveryKind,conversation)`、`(host,requestId)`，**没有** work/subtask 的 owner 唯一键，也没有租约或 fencing 版本；A21 只测重复事件与双客户端，测不到两个 Bot 同刻认领同一子任务。
- **最小修订**：增加 `(goalId, subtaskId)` 上的 owner 唯一约束 + 租约版本/fencing token + 平局仲裁规则（先落库者得，失败方必须重读后重新 decide）；A 矩阵补一行“两 Bot 同刻认领 → 仅一 owner、另一方向用户可见放弃原因、无双成本”。

### P1-2 §13 / §17 / §19：后台服务是两客户端与 A06/A21 的前置，却不在任何硬门槛里
- **冲突**：§13 明确“服务安装/升级/版本握手是独立交付项”，A06（同一 Agent 接入 xiaok 协作空间）与 A21（两客户端同时启动）都依赖它；但 §17 P0a/P0b 硬门槛均未列入，§19 反把“服务拆分/安装方式”列为实施中再收敛的选择。结果是 P0b 可能靠两个 Main 各自跑通而“验收通过”，正好撞上 §13 明文禁止的形态。
- **最小修订**：§17 P0a 门槛加“服务可安装、版本握手、版本不兼容时只读降级”；P0b 门槛加“关闭任一客户端不影响已授权后台工作、无双写双调度”；§19 把“安装方式”从纯选择项移为需在 P0a 结项前定稿的交付项。

### P1-3 §8：默认预算把“触发扇出”和“单次执行时长”混为一谈
- **冲突**：“每个外部触发最多6次Bot执行、10分钟、同一工作最多2轮往返”。本地开发场景（§2）与 A05 要求真实执行+可核验产物，构建/测试很容易超过 10 分钟；若按字面实现为 run 允许时长，A05 与 A12 会互相排斥（A12 要求硬停，A05 要求真实跑完）。
- **最小修订**：拆成三类预算：①触发扇出（次数/往返/tokens）②单 run 时长（按任务类型或按项目配置）③无进展检测（例如 N 分钟无新事件/无产物增量即挂起并保存检查点）。明确 10 分钟只约束“无进展的自主循环”，不是合法长任务的硬中断。

### P1-4 §14 / §5 / §18-A18、A20：已读用“最大消息序列”表示，与未读/定位原消息冲突
- **冲突**：§5 要求“需要我处理”可定位原消息、进行中不刷成未读；§14 却只用单个“用户真正看到的最大消息序列”作 Read。用户从通知直接跳到最新主动消息时，最大序列越过中间未读，这些消息会被算作已读，A18/A20 的“未读仍可见”无法稳定成立。
- **最小修订**：改为按消息已读集合（或 `(conversation, messageId)` 区间集合）记录；明确“跳转/通知点击不等于置读”，仅当消息在视口内停留达到条件才置读；在 A20 增一条“跳过中间消息后中间未读仍出现在需要我处理”。

### P1-5 §3.2 / §11.4 / §18-A06：canonical ID 只写“归一”，没有权威解析点与旧 ID 迁移规则
- **冲突**：文档承认 registry 用 `xiaok-cli`、Room 部分分支识别 `xiaok`，要求“P0 先归一并验合同”；但未定义 canonical 集合、别名表归属、已持久化绑定（bot→`xiaok`）的迁移与去重规则。A06 只比“相同绑定/权限/能力结果”，测不到同一 Agent 被登记成两条绑定，或旧 ID 解析失败被当成“未安装”。
- **最小修订**：§11.4 指定唯一解析点为共享服务，附别名表（至少 `xiaok`↔`xiaok-cli`）；写入时按 canonical 去重，旧 ID 只读解析并给一次迁移提示；P0a 合同测试断言“同一 Agent 在项目 registry / Room / 新 App 三处解析到同一 bindingId 与同一能力矩阵，且不产生重复绑定”。

### P1-6 §6.4 vs §7 / §8：建群首轮可能等价于全员模型调用，且未纳入预算
- **冲突**：§6.4 要求“系统选相关成员形成第一轮工作理解：可做的下一步、责任人、依赖和完成标准”，而 §7/§8 禁止默认广播唤醒、要求“无必要时安静”，成本又在 §16/A26 计入。文档没写首轮参与上限、是否计入扇出预算，也没写与 A11 的关系，读者会实现成“每个成员各出一份理解”。
- **最小修订**：明确首轮为一次性 setup 成本：按“目标拆出的子任务 × 能力矩阵”匹配成员，上限 N 个模型调用，由一个协调 pass 汇总为分工草案；不要每个成员独立长篇输出；在 §16 注明首轮与后续扇出分别计费。

## P2（不阻断当前阶段，进入对应实现前需补）
