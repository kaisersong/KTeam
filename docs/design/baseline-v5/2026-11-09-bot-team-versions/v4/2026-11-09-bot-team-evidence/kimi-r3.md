1. §6 步骤 4 与 §18.1 探针计数衔接  
   具体冲突：“协调 pass”是否计入 §18.1 的“每条至多一次语义 router 调用”未显式写明，实施团队可能把草案生成与成员唤醒分别计数，导致探针口径不一。  
   最小修订：在 §6 步骤 4 增加一句——“首轮协调 pass 即 §18.1 所述唯一语义 router 调用，其输出至多唤醒 3 个候选成员进入 accept/claim CAS，router 调用与成员执行分别计入路由预算与执行预算。”

2. §9.2 跨设备“全部已读”的 cursor 收敛  
   具体冲突：已读区间/连续水位在同一用户多客户端场景下可能因并发上报产生重叠区间或顺序倒置，正文只写了“显式‘全部已读’才合并区间”，未说明多设备冲突裁决。  
   最小修订：补充“read writer 以用户+conversation 为单写 owner，按 server sequence 单调合并稀疏区间；客户端上报须携带 lastKnownCursor，服务端拒绝乱序/回退写入并令客户端重读。”

3. §15.1 “对外 API 写入”与本地同步目录的边界示例  
   具体冲突：Dropbox/iCloud/OneDrive 等本地目录同步在文件系统层面表现为项目文件写，实际会外发到云端；实施者可能将其误判为“项目内文件修改”而自动执行。  
   最小修订：在 §15.1 动作表“项目内文件修改”后加限定——“不含向公共云同步目录的写入；任何会触发外部同步服务的目录/文件写按‘上传私人材料/对外 API 写入’确认。”

4. §18.1 探针的模型/温度/采样版本冻结  
   具体冲突：探针门槛依赖模型行为，但未明确要求冻结探针所用模型版本与采样参数，不同版本重跑可能导致门槛不可比。  
   最小修订：在 §18.1 增加——“探针语料、标签、模型版本、采样温度/top-p、router 与成员执行模型 identity 一并冻结；任何变更须重跑完整 40 条集合并更新冻结记录。”

5. §11.5 canonical registry 引入期的负例清单
